# V0.3 — OPENAPI GENERATOR

## Estado

Versión: V0.3.0
Nombre: OpenAPI Generator
Estado: PLANIFICACIÓN / INSPECCIÓN
Prerequisito: V0.2.0
Tag base: v0.2.0

---

# 1. OBJETIVO

Implementar un generador capaz de transformar la metadata estructurada producida por el Analyzer V0.2 en una especificación OpenAPI válida y reproducible.

Flujo objetivo:

Java / Spring Boot
        ↓
Analyzer V0.2
        ↓
AnalysisResult
        ↓
OpenAPI Generator
        ↓
OpenAPI 3.x
        ↓
openapi.yaml / openapi.json

El Generator NO debe analizar directamente código Java.

Su entrada conceptual debe ser la metadata producida por:

    analyzer.AnalysisResult

El Generator debe consumir metadata, no volver a interpretar Java.

---

# 2. PRINCIPIOS

## 2.1 Separación de responsabilidades

Analyzer:

    Java → Metadata

Generator:

    Metadata → OpenAPI

No mezclar ambas responsabilidades.

El Generator no debe importar ni utilizar directamente:

- javalang
- spring_boot_analyzer.py
- ast_analyzer.py
- dto_analyzer.py
- scanner.py

El Generator debe trabajar exclusivamente sobre el modelo público de metadata.

---

## 2.2 Evidencia > inferencia

El Generator no debe inventar información que el Analyzer no haya producido.

Si una propiedad necesaria para OpenAPI no existe en la metadata:

- no inventarla;
- no inferirla arbitrariamente;
- utilizar un comportamiento OpenAPI conservador;
- o generar un Diagnostic cuando corresponda.

Ejemplo:

Si un endpoint no tiene información suficiente para determinar un response:

NO asumir automáticamente:

    200 application/json

sin evidencia.

La decisión debe documentarse.

---

## 2.3 Compatibilidad

V0.3 debe preservar las capacidades existentes de V0.2.

Los 84 tests existentes deben continuar pasando.

No eliminar comportamiento existente salvo autorización explícita.

---

## 2.4 Dependencias

No agregar dependencias simplemente por comodidad.

Cualquier nueva dependencia runtime debe justificar:

1. necesidad técnica real;
2. limitación concreta de la implementación estándar;
3. impacto de instalación;
4. licencia;
5. mantenimiento;
6. impacto en arquitectura;
7. cobertura mediante tests.

Primero evaluar si OpenAPI puede generarse correctamente utilizando:

- Python standard library;
- estructuras propias;
- serialización YAML/JSON controlada.

No introducir automáticamente una librería OpenAPI.

### Components / Schemas

Generar:

    components:
      schemas:

para DTOs identificados por el Analyzer.

Soportar:

- objetos;
- propiedades;
- tipos primitivos;
- enums;
- colecciones;
- DTOs anidados;
- referencias $ref;
- ciclos;
- validaciones representables.

Evitar duplicar schemas.

Un mismo DTO debe producir un schema reutilizable cuando la metadata permita identificarlo inequívocamente.

---

### Bean Validation

Mapear, cuando corresponda:

- @NotNull
- @NotBlank
- @NotEmpty
- @Size
- @Min
- @Max
- @Email
- @Pattern
- @Positive
- @PositiveOrZero
- @Negative
- @NegativeOrZero

Debe evaluarse cómo representar cada validación en OpenAPI.

Ejemplos potenciales:

@NotNull
    → required

@Size(min=2,max=50)
    → minLength / maxLength

@Min(1)
    → minimum

@Max(100)
    → maximum

@Email
    → format: email

@Pattern
    → pattern

No realizar conversiones semánticamente dudosas.

---

### Security

Consumir la evidencia de seguridad producida por V0.2.

Evaluar cómo representar:

- @PreAuthorize
- @Secured

en OpenAPI.

No implementar un analizador de Spring Security.

La representación debe ser conservadora y documentada.

---

### consumes / produces

Mapear:

- consumes;
- produces;

a los mecanismos correspondientes de OpenAPI.

Evaluar correctamente:

- método;
- clase;
- herencia de valores;
- ausencia de información.

---

### Evidence / Diagnostics

El Generator debe preservar la trazabilidad cuando sea útil.

Los errores o situaciones no representables deben producir diagnostics claros.

---

### Salidas

Evaluar generación de:

    openapi.yaml

y:

    openapi.json

La decisión final debe quedar documentada.

# 12. DETERMINISMO

La generación debe ser determinista.

Para la misma metadata de entrada:

    AnalysisResult A

debe producir exactamente la misma especificación:

    OpenAPI A

en ejecuciones repetidas.

Evitar:

- orden aleatorio;
- IDs aleatorios;
- timestamps automáticos;
- información dependiente del entorno.

El orden de paths, schemas, parameters y operaciones debe ser estable.

---

# 13. OPERATION ID

Debe definirse una estrategia determinista para operationId.

Ejemplo:

    getCustomerById

o equivalente.

No utilizar hashes ni identificadores aleatorios.

Si existe información insuficiente para producir un operationId semántico, debe definirse una estrategia documentada.

Evitar colisiones.

Debe existir test específico para:

- nombres repetidos;
- métodos sobrecargados;
- controllers diferentes;
- endpoints con paths similares.

---

# 14. SCHEMAS Y $REF

Los DTOs deben convertirse preferentemente en schemas reutilizables.

Ejemplo:

    CustomerResponse

debe aparecer una sola vez:

    components.schemas.CustomerResponse

y los endpoints deben utilizar:

    $ref: "#/components/schemas/CustomerResponse"

No duplicar inline schemas innecesariamente.

Debe existir protección contra:

    Customer → Address → Customer

y otros ciclos.

Los ciclos deben producir referencias válidas, no recursión infinita.
