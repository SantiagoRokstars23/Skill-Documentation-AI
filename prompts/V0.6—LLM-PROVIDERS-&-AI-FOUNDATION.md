# V0.6 — LLM PROVIDERS & AI FOUNDATION

## Objetivo

Incorporar una infraestructura desacoplada para trabajar con Large Language Models (LLM), permitiendo que futuras capacidades de IA del proyecto puedan utilizar diferentes proveedores sin acoplar la lógica de negocio a un proveedor concreto.

V0.6 construye la infraestructura base.

NO implementa todavía las capacidades inteligentes finales del producto.

La arquitectura futura deberá permitir evolucionar hacia:

Proyecto Java
    │
    ▼
 Analyzer
    │
    ▼
 OpenAPI Generator
    │
    ▼
 Validator
    │
    ▼
 AI / LLM Layer
    │
    ├── documentación inteligente
    ├── análisis semántico
    ├── recomendaciones
    ├── explicación de diagnostics
    └── automatizaciones futuras

Pero ninguna de esas capacidades se implementa en V0.6.

# 3. OBJETIVO ARQUITECTÓNICO

La arquitectura deberá separar:

- contrato del proveedor;
- configuración;
- implementación concreta;
- manejo de errores;
- consumidor futuro.

Conceptualmente:

Application / Future AI Features
             │
             ▼
       LLM Provider API
             │
      ┌──────┼──────┐
      ▼      ▼      ▼
   Provider A   Provider B
      │            │
      ▼            ▼
 External API   Local/API


El consumidor deberá depender de la abstracción, no de una implementación concreta.

La arquitectura concreta debe determinarse en FASE 2 después de inspeccionar el código existente.

No asumir que debe utilizarse una clase abstracta, Protocol, registry, factory u otro patrón hasta justificarlo.

---

# 4. API DEL PROVIDER

Debe existir una API pública y estable para interactuar con un proveedor LLM.

Como mínimo deberá representar conceptualmente:

- prompt/instrucción;
- modelo, si aplica;
- configuración básica;
- generación de texto;
- respuesta;
- errores.

La API exacta debe determinarse en FASE 2.

La solución debe evitar sobreingeniería.

No introducir todavía:

- agentes;
- memoria;
- RAG;
- embeddings;
- vector databases;
- workflows multiagente;
- tool calling avanzado;
- MCP;
- streaming obligatorio;
- function calling complejo.

---

# 5. PROVIDERS CONCRETOS

La FASE 2 deberá determinar si V0.6 necesita:

- únicamente una implementación Fake/Mock;
- un provider local;
- un provider comercial real;
- más de un provider.

La directriz NO obliga a implementar un proveedor comercial concreto.

Si se propone implementar un provider real, FASE 2 deberá justificar:

- por qué es necesario en V0.6;
- qué proveedor;
- qué mecanismo de comunicación;
- si requiere SDK;
- si puede utilizarse HTTP estándar;
- impacto en dependencias;
- manejo de credenciales;
- impacto en testing.

No implementar múltiples proveedores comerciales únicamente para demostrar compatibilidad.

La prioridad es establecer una abstracción correcta.

---

# 6. PROVIDER FAKE / MOCK

Debe existir una estrategia para probar la infraestructura sin depender de servicios externos.

La solución puede utilizar:

- Fake Provider;
- Mock Provider;
- implementación determinista;
- otra alternativa equivalente.

La decisión corresponde a FASE 2.

Los tests no deben requerir:

- Internet;
- API keys reales;
- cuentas de proveedores;
- servicios externos;
- consumo de tokens;
- costes de inferencia.

---

# 7. CONFIGURACIÓN

Debe definirse una estrategia segura para configurar proveedores.

Como mínimo deberá contemplarse:

- proveedor seleccionado;
- modelo;
- API key o credencial;
- parámetros básicos.

Las credenciales:

- nunca deben hardcodearse;
- nunca deben almacenarse en Git;
- nunca deben aparecer en logs;
- nunca deben aparecer en tests;
- nunca deben aparecer en mensajes de error.

La fuente concreta de configuración debe determinarse en FASE 2.

No asumir automáticamente `.env`, variables de entorno, archivos YAML u otro mecanismo sin inspección previa.

---

# 8. ERRORES

La infraestructura debe contemplar una estrategia consistente para errores como:

- proveedor no configurado;
- proveedor desconocido;
- credencial ausente;
- modelo inválido;
- timeout;
- error HTTP;
- respuesta inválida;
- error del proveedor.

La FASE 2 deberá determinar si se crea una jerarquía propia de excepciones o se utiliza otro mecanismo.

Los errores de proveedores no deben acoplar el resto del proyecto a excepciones específicas de un SDK.

---

# 9. SEPARACIÓN DE RESPONSABILIDADES

Los componentes actuales deben continuar desacoplados:

Analyzer
Generator
Validator
CLI
Providers

V0.6 NO debe hacer que:

- Analyzer invoque LLM;
- Generator invoque LLM;
- Validator invoque LLM;
- CLI requiera LLM para funcionar.

La infraestructura de Providers debe poder existir sin alterar el flujo actual:

analyze
generate
validate

La futura integración con capacidades de IA pertenece a versiones posteriores, salvo autorización explícita.

- spring-doc chat

3. nuevas dependencias solo cuando sean necesarias;

- OpenAI;
- Anthropic;
- Gemini;
- otros proveedores.

V0.6 no debe convertirse en un agregador de SDKs.

- contrato del Provider;
- implementación Fake/Mock;
- configuración;
- selección del provider, si existe;
- errores;
- credenciales ausentes;
- proveedor desconocido;
- comportamiento determinista;
- aislamiento respecto a servicios externos;
- ausencia de secretos;
- compatibilidad con la API existente.

Además:

- todos los tests históricos deben continuar pasando;
- ningún test debe necesitar Internet;
- ningún test debe necesitar una API key;
- ningún test debe generar coste externo.

La FASE 2 deberá proponer la distribución de los tests y su cantidad aproximada.

---

# 13. DETERMINISMO

La infraestructura debe ser determinista cuando se utilicen providers Fake/Mock.

No depender de:

- timestamps;
- UUID aleatorios;
- orden no determinista;
- servicios externos;
- respuestas variables de modelos reales.

Si se implementa un provider real, sus tests deberán aislarse de la red.

---

# 14. INMUTABILIDAD Y AISLAMIENTO

Cuando corresponda, la infraestructura no deberá modificar objetos de configuración o datos recibidos inesperadamente.

Los componentes existentes no deben adquirir dependencias implícitas sobre Providers.

Debe verificarse mediante tests que Analyzer, Generator, Validator y CLI continúan funcionando sin configurar ningún LLM.

# 22. CRITERIO PRINCIPAL DE V0.6

V0.6 NO busca hacer al proyecto inteligente.

Busca construir el fundamento que permita hacerlo inteligentemente después.

La meta es pasar de:

"El proyecto tiene una interfaz LLM"

a:

"El proyecto tiene una infraestructura de Providers preparada para que futuras capacidades de IA puedan conectarse sin acoplarse a un proveedor específico."

La calidad de la abstracción y el aislamiento son más importantes que la cantidad de proveedores implementados.
