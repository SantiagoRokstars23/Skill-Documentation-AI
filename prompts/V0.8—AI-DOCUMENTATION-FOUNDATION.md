# 0. OBJETIVO

V0.8 convierte la infraestructura LLM construida en V0.6/V0.7 en un consumidor real dentro del motor.

Hasta V0.7 el proyecto dispone de:

- Analyzer para analizar proyectos Java/Spring Boot.
- Generator para producir OpenAPI.
- Validator para validar OpenAPI.
- CLI para operar el motor.
- LLMProvider como abstracción.
- FakeProvider para pruebas.
- AnthropicProvider como proveedor LLM real.

V0.8 debe construir la primera capa que conecte:

    Proyecto Spring Boot
          ↓
       Analyzer
          ↓
    AnalysisResult
          ↓
    ContextBuilder
          ↓
     PromptEngine
          ↓
      LLMProvider
          ↓
   DocumentationResult
          ↓
   salida estructurada

El objetivo NO es crear todavía un sistema completo de agentes, RAG, memoria, chat o automatización empresarial.

El objetivo es demostrar que el motor puede tomar información estructurada de un microservicio Spring Boot y utilizar un LLM para generar documentación técnica útil, reproducible y estructurada.

---

# 1. RESULTADO ESPERADO DE V0.8

Al finalizar V0.8 debe ser posible ejecutar conceptualmente:

    Spring Boot project
        ↓
    Analyzer
        ↓
    AI Documentation Engine
        ↓
    LLM Provider
        ↓
    DocumentationResult

El sistema debe poder generar, como mínimo:

- descripción de la API/proyecto;
- descripción de cada endpoint;
- explicación de parámetros;
- explicación de request body;
- explicación de responses;
- descripción de DTOs relevantes;
- información suficiente para enriquecer documentación OpenAPI existente.

La generación debe basarse EXCLUSIVAMENTE en información proporcionada por el Analyzer/OpenAPI/contexto explícito.

El LLM no debe inventar comportamiento del sistema.

Cuando la información no sea suficiente, el resultado debe indicarlo en lugar de inventarlo.

# 5. REGLA SOBRE INFORMACIÓN Y ALUCINACIONES

Esta es una de las reglas más importantes de V0.8.

El LLM solo puede utilizar información presente en el contexto entregado.

El sistema debe instruir al LLM explícitamente:

- no inventar endpoints;
- no inventar parámetros;
- no inventar códigos HTTP;
- no inventar reglas de negocio;
- no inventar autenticación;
- no inventar nombres de entidades;
- no asumir comportamiento que no esté representado;
- diferenciar hechos de inferencias;
- utilizar "No determinado por el análisis" cuando corresponda.

El sistema NO debe intentar solucionar la falta de información inventando información.

NO debe generar prompts.

    class DocumentationContextBuilder:

        def build(
            self,
            analysis_result: AnalysisResult,
            openapi_document: dict | None = None

            ...

# 16. PARSEO DE RESPUESTA

El sistema debe separar:

    LLM response
          ↓
    parsing
          ↓
    validation
          ↓
    DocumentationResult

Una respuesta inválida del LLM no debe producir un DocumentationResult aparentemente válido.

Debe existir un mecanismo de error explícito.

No utilizar heurísticas frágiles como:

- split("```");
- buscar llaves arbitrariamente;
- regex para "arreglar" JSON;
- eliminar texto hasta encontrar "{";
- inventar valores faltantes.

Si se decide tolerar markdown fences, debe estar justificado y testeado.

# 18. PROVIDER ERROR VS DOCUMENTATION ERROR

Un timeout de Anthropic:

    ProviderTimeoutError

Una respuesta HTTP inválida:

    ProviderRequestError

    DocumentationParseError

No mezclar responsabilidades.
