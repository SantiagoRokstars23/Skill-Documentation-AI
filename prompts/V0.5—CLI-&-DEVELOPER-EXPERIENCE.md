# V0.5 — CLI & DEVELOPER EXPERIENCE

## 1. Objetivo

V0.5 tiene como objetivo convertir el núcleo técnico construido en V0.1–V0.4 en una herramienta utilizable desde terminal.

El proyecto actualmente dispone de:

- Analyzer de proyectos Spring Boot.
- AnalysisResult y modelos públicos.
- análisis AST + fallback.
- OpenAPI Generator.
- generación OpenAPI 3.0.3.
- salida JSON/YAML.
- OpenAPI Validator.
- Diagnostics reutilizables.
- 260+ tests.
- documentación y versionado por releases.

V0.5 NO debe reimplementar ninguna de esas capacidades.

Debe crear una capa CLI delgada que orqueste las capacidades existentes.

---

## 2. Flujo objetivo

El flujo conceptual es:

    Proyecto Spring Boot
            ↓
          CLI
            ↓
        Analyzer
            ↓
       AnalysisResult
            ↓
     OpenAPI Generator
            ↓
       OpenAPI 3.0.3
            ↓
        Validator
            ↓
       Diagnostics
            ↓
       Output/Report

La CLI debe actuar como orquestador.

No debe contener lógica de análisis Java, generación OpenAPI ni validación OpenAPI.

---

## 3. Scope Lock

V0.5 incluye exclusivamente:

- CLI.
- comandos de análisis.
- generación OpenAPI desde proyecto.
- validación de OpenAPI.
- integración entre Analyzer/Generator/Validator.
- outputs de terminal.
- output JSON estructurado.
- códigos de salida.
- manejo de errores de CLI.
- tests de CLI.
- documentación de uso.

V0.5 NO incluye:

- LLM.
- Claude.
- Gemini.
- OpenAI.
- RAG.
- MCP.
- agentes.
- Confluence.
- CI/CD.
- Docker.
- API HTTP.
- Swagger UI.
- generación de SDK/clientes/servidores.
- base de datos.
- interfaz gráfica.
- autenticación.
- cloud.
- Auditor avanzado.
- Drift Detection.

No agregar funcionalidades fuera de este alcance.

## 4. Protocolo obligatorio

La implementación debe realizarse en cuatro fases.

### FASE 1 — INSPECCIÓN

Solo lectura.

No modificar, crear ni eliminar archivos.

Inspeccionar como mínimo:

- pyproject.toml
- analyzer/
- generators/
- validator/
- tests/
- examples/
- README.md
- CLAUDE.md
- docs/03-Arquitectura.md
- docs/12-Roadmap.md
- docs/13-Versionado.md
- CHANGELOG.md

Verificar:

- APIs públicas existentes.
- punto correcto de integración.
- empaquetado.
- dependencias.
- compatibilidad Python.
- estado de tests.
- cómo se ejecutan actualmente Analyzer/Generator/Validator.
- si existe ya algún entry point.
- posibles conflictos con el paquete validators/ histórico.

Entregar reporte de Fase 1.

NO implementar.

---

### FASE 2 — DECISIÓN ARQUITECTÓNICA

No implementar todavía.

Proponer y justificar:

1. Tecnología para CLI.

Evaluar stdlib argparse frente a dependencias externas.

Prioridad:

- mínima dependencia;
- multiplataforma;
- mantenibilidad;
- instalación sencilla.

2. Estructura de comandos.

Proponer como mínimo evaluar:

    analyze
    generate
    validate

y determinar si conviene:

    analyze <project>
    generate <project>
    validate <openapi>

o un flujo combinado.

3. Entry point.

Evaluar configuración de pyproject.toml para permitir:

    spring-doc ...

o el nombre CLI que se determine.

4. Opciones.

Evaluar:

    --format json|yaml
    --output <path>
    --openapi
    --strict
    --quiet
    --verbose
    --json

No implementar opciones innecesarias.

5. Exit codes.

Definir comportamiento determinista.

Como mínimo diferenciar:

    0 = éxito
    >0 = error de ejecución/validación

Determinar si warnings deben producir exit code distinto bajo --strict.

6. Output.

Diseñar dos modos:

Human-readable:

    ✓ Analysis completed
    Controllers: 12
    Endpoints: 47
    DTOs: 21
    Warnings: 3
    Errors: 0

Machine-readable:

    --json

que produzca JSON estable y parseable.

7. Errores.

La CLI no debe mostrar stack traces innecesarios para errores normales de usuario.

Ejemplos:

- proyecto inexistente;
- archivo inexistente;
- OpenAPI inválido;
- formato desconocido;
- ruta de salida inválida.

Los errores internos inesperados deben diferenciarse de errores de entrada.

8. Compatibilidad.

Evaluar Windows, Linux y macOS.

No asumir shell específico.

9. Integración.

La CLI debe importar únicamente las APIs públicas.

No acceder directamente a:

- ast_analyzer.py
- ast_backend.py
- dto_analyzer.py
- spring_boot_analyzer.py
- scanner.py
- openapi_types.py
- openapi_schemas.py
- openapi_rules.py

salvo que la API pública existente no sea suficiente.

Si alguna API pública resulta insuficiente, demostrarlo antes de modificar modelos.

10. Arquitectura.

Preferir una capa CLI pequeña.

No duplicar lógica existente.

No crear una arquitectura de plugins ni un framework interno.

Entregar reporte de Fase 2 y esperar autorización.

---

## 5. API conceptual esperada

La CLI debería permitir conceptualmente:

    spring-doc analyze ./project

    spring-doc generate ./project --format yaml

    spring-doc generate ./project --format json --output openapi.json

    spring-doc validate openapi.yaml

y evaluar si conviene un comando combinado:

    spring-doc analyze ./project --openapi

No asumir que todos deben implementarse exactamente así.

La decisión corresponde a Fase 2.

---

## 6. Testing

Conservar todos los tests existentes.

Actualmente deben mantenerse como regresión.

Agregar tests para:

- help;
- versión;
- comando desconocido;
- proyecto inexistente;
- proyecto válido;
- generate JSON;
- generate YAML;
- output a archivo;
- validate JSON;
- validate YAML;
- OpenAPI inválido;
- warnings;
- errors;
- --strict;
- --json;
- códigos de salida;
- determinismo;
- rutas Windows/Linux de forma portable;
- integración real con examples/customer-service.

No crear tests frágiles dependientes de colores, espacios exactos o mensajes decorativos.

---

## 7. Definition of Done

V0.5 estará terminada cuando:

1. La CLI pueda instalarse mediante el paquete Python.
2. Exista un entry point funcional.
3. El usuario pueda analizar un proyecto Spring Boot.
4. El usuario pueda generar OpenAPI.
5. El usuario pueda validar OpenAPI.
6. JSON y YAML funcionen.
7. Exista output humano.
8. Exista output --json.
9. Existan exit codes deterministas.
10. Exista --strict si Fase 2 lo justifica.
11. Los errores de usuario sean manejados correctamente.
12. Los 260+ tests existentes continúen pasando.
13. Los nuevos tests cubran la CLI.
14. La CLI funcione en Windows/Linux/macOS.
15. No se haya introducido lógica duplicada.
16. No se hayan modificado Analyzer/Generator/Validator salvo justificación explícita.
17. Scope Lock respetado.
18. Documentación actualizada.
19. Versionado actualizado a 0.5.0.
20. Revisión pre-commit completada.
21. Commit solo después de autorización.
22. Tag solo después de autorización.

---

## 8. Regla fundamental

La CLI es una capa de presentación/orquestación.

NO debe convertirse en otro Analyzer.

NO debe convertirse en otro Generator.

NO debe convertirse en otro Validator.

Debe conectar correctamente las piezas existentes.
