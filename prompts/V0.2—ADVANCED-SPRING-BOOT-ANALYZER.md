============================================================
1. OBJETIVO DE V0.2
============================================================

V0.2 tiene como objetivo transformar el Analyzer de V0.1
de un detector básico de endpoints en un Analyzer estructural
capaz de construir un modelo semántico más completo de un
microservicio Java/Spring Boot.

La finalidad NO es generar todavía OpenAPI.

La finalidad es producir información estructurada y trazable
que posteriormente pueda ser utilizada por:

- OpenAPI Generator.
- Validators.
- Auditor.
- Skill.
- LLM Providers.

El resultado conceptual esperado es:

Java/Spring Boot
        ↓
Java Structure Analysis
        ↓
Spring Boot Analysis
        ↓
Structured Microservice Model
        ↓
Evidence
        ↓
futuras fases:
OpenAPI / Skill / LLM / Auditor

============================================================
2. PRINCIPIO FUNDAMENTAL
============================================================

El Analyzer debe responder:

"¿Qué existe realmente en el código?"

NO debe responder:

"¿Cómo debería documentarse?"

NO debe inventar información.

NO debe completar información ausente mediante suposiciones.

NO debe utilizar un LLM para interpretar el código en V0.2.

Toda información extraída debe poder relacionarse con evidencia
real del código fuente cuando sea posible.

Regla:

CODE → EVIDENCE → STRUCTURED MODEL

No:

CODE → SUPOSICIÓN → DOCUMENTACIÓN

4. REGLAS DE GOBIERNO
============================================================

REGLA 1 — NO CAMBIAR LA ARQUITECTURA SIN AUTORIZACIÓN

No modificar la arquitectura global del proyecto.

Se permite refactorizar internamente analyzer/ cuando sea
necesario para cumplir V0.2.

La refactorización debe:

- mantener responsabilidades claras;
- evitar acoplamiento;
- mantener interfaces públicas compatibles cuando sea posible;
- estar justificada.

------------------------------------------------------------

REGLA 2 — NO INTRODUCIR DEPENDENCIAS INNECESARIAS

El proyecto debe continuar utilizando Python como lenguaje.

No agregar dependencias únicamente por comodidad.

Toda nueva dependencia debe:

1. Tener una justificación técnica.
2. Resolver una limitación real.
3. Ser compatible con el proyecto.
4. Estar documentada.
5. Tener impacto evaluado.
6. Tener cobertura de pruebas.

------------------------------------------------------------

REGLA 3 — AST VS REGEX

Antes de modificar sustancialmente el parser actual, realizar una
evaluación técnica entre:

A. Estrategia actual:
   Regex + parsing estructural + balanceo.

B. Parser AST de Java.

La evaluación debe considerar:

- precisión;
- robustez;
- anotaciones;
- tipos;
- genéricos;
- métodos;
- clases;
- DTOs;
- herencia;
- rendimiento;
- complejidad;
- mantenimiento;
- dependencias;
- portabilidad;
- facilidad de instalación.

NO introducir un parser AST automáticamente.

NO mantener Regex automáticamente.

Seleccionar la alternativa técnicamente más apropiada para
el alcance de V0.2.

La decisión debe documentarse.

------------------------------------------------------------

REGLA 4 — NO ACOPLAR A UN LLM

V0.2 debe funcionar completamente sin ningún LLM.

No implementar:

- OpenAI;
- Claude;
- Gemini;
- Anthropic;

- modelos locales;
- APIs externas de IA.

REGLA 5 — NO INVENTAR INFORMACIÓN

5. CAPACIDADES V0.2
============================================================

------------------------------------------------------------
5.1 CONTROLLERS
------------------------------------------------------------

Mejorar el análisis de Controllers.

Debe soportar, cuando sea técnicamente posible:

- @RestController
- @Controller cuando sea relevante al modelo
- @RequestMapping a nivel de clase
- mappings HTTP
- anotaciones fully-qualified
- controllers con diferentes modificadores
- métodos package-private
- mappings heredados cuando la estrategia elegida lo permita

No asumir comportamiento que no pueda demostrarse.

------------------------------------------------------------
5.2 ENDPOINTS
------------------------------------------------------------

El Analyzer debe obtener:

- HTTP method
- path
- controller
- método Java
- parámetros
- consumes
- produces
- response information
- security evidence cuando exista
- evidence

Debe soportar:

- GET
- POST
- PUT
- DELETE
- PATCH

Y:

@RequestMapping(method = ...)

Debe evaluar correctamente mappings con:

- value
- path
- method
- consumes
- produces

------------------------------------------------------------
5.3 PARAMETERS
------------------------------------------------------------

Ampliar el soporte de parámetros.

Debe contemplar:

- @PathVariable
- @RequestParam
- @RequestBody
- @RequestHeader

Debe identificar:

- nombre;
- tipo;
- origen;
- required;
- defaultValue;
- anotaciones relevantes;
- validaciones;
- evidence.

Debe soportar tipos complejos y genéricos cuando sea posible.

------------------------------------------------------------
5.4 DTO ANALYSIS
------------------------------------------------------------

V0.2 debe ser capaz de localizar y analizar DTOs referenciados
por endpoints.

Ejemplo:

CustomerRequest

Debe poder identificar, cuando sea posible:

- clase;
- campos;
- tipos;
- modificadores relevantes;
- validaciones;
- nested DTOs;
- colecciones;
- tipos genéricos;
- enums.

Ejemplo:

class CustomerRequest {

    @NotBlank
    private String name;

    @Email
    private String email;

    private Integer age;
}

Debe producir un modelo estructurado equivalente.

IMPORTANTE:

No generar JSON OpenAPI.

No generar documentación.

Solo metadata estructurada.

------------------------------------------------------------
5.5 RESPONSE ANALYSIS
------------------------------------------------------------

Detectar información de respuesta.

Debe contemplar, cuando sea posible:

- return type;
- ResponseEntity<T>;
- tipos genéricos;
- colecciones;
- DTOs;
- @ResponseStatus.

Ejemplo:

ResponseEntity<CustomerResponse>

Debe conservar:

wrapper:
ResponseEntity

body:
CustomerResponse

------------------------------------------------------------
5.6 VALIDATIONS
------------------------------------------------------------

Detectar anotaciones comunes de Bean Validation.

Como mínimo evaluar:

- @NotNull
- @NotBlank
- @NotEmpty
- @Size
- @Min
- @Max
- @Email
- @Pattern
- @Positive
- @PositiveOrZero
- @Negative
- @NegativeOrZero

La arquitectura debe permitir ampliar la lista posteriormente.

No es necesario soportar todas las anotaciones existentes en
Bean Validation.

------------------------------------------------------------
5.7 HEADERS
------------------------------------------------------------

Detectar:

@RequestHeader

Debe capturar:

- nombre;
- tipo;
- required;
- defaultValue;
- evidence.

------------------------------------------------------------
5.8 CONSUMES / PRODUCES
------------------------------------------------------------

Extraer cuando existan:

consumes
produces

desde:

@RequestMapping
@GetMapping
@PostMapping
@PutMapping
@DeleteMapping
@PatchMapping

La información debe conservarse como metadata.

------------------------------------------------------------
5.9 SECURITY
------------------------------------------------------------

Extraer evidencia básica de anotaciones de seguridad cuando
puedan identificarse de forma determinística.

Evaluar como mínimo:

- @PreAuthorize
- @Secured

No implementar un analizador completo de Spring Security.

El objetivo es solamente capturar evidencia.

------------------------------------------------------------
5.10 EVIDENCE
------------------------------------------------------------

Mejorar Evidence.

La estructura debe permitir representar como mínimo:

- file
- line
- symbol
- type

Ejemplo:

{
  "file": "CustomerController.java",
  "line": 42,
  "symbol": "createCustomer",
  "type": "endpoint"
}

La evidencia debe utilizarse también para:

- DTOs;
- fields;
- parameters;
- validations;
- responses;
- security.

------------------------------------------------------------
5.11 DIAGNOSTICS
------------------------------------------------------------

Evaluar la evolución de:

warnings: list[str]

hacia diagnostics estructurados.

Como mínimo evaluar:

- severity;
- code;
- message;
- evidence.

Ejemplo:

{
  "severity": "WARNING",
  "code": "ANALYZER_UNCLOSED_CLASS",
  "message": "...",
  "evidence": {...}
}

No ocultar silenciosamente errores estructurales importantes.
