V0.7 — LLM REAL PROVIDER & AI FOUNDATION

OBJETIVO

V0.7 debe incorporar el primer proveedor LLM real al proyecto Skill-Documentation-AI.

El objetivo de esta versión NO es implementar documentación inteligente completa, agentes, RAG ni integración con la CLI.

El objetivo es demostrar que la infraestructura de providers creada en V0.6 puede comunicarse de forma segura y desacoplada con un proveedor LLM real.

V0.7 debe dejar preparada la base para que V0.8 pueda utilizar un LLM para mejorar la documentación de microservicios Java Spring Boot.

==================================================
1. PRINCIPIOS
==================================================

1. El núcleo determinístico del proyecto sigue siendo independiente del LLM.

2. Analyzer, Generator, Validator y CLI no deben depender obligatoriamente de un proveedor LLM.

3. LLMProvider continúa siendo el contrato de abstracción.

4. El proveedor real debe ser intercambiable por FakeProvider sin modificar al consumidor.

5. No se permite hardcodear API keys, modelos ni credenciales.

6. Los tests nunca deben realizar llamadas reales a Internet.

7. Las credenciales nunca deben aparecer en logs, excepciones, reportes ni snapshots.

8. No se incorpora un SDK comercial si puede evitarse razonablemente mediante stdlib.

9. No se implementan funcionalidades especulativas.

10. La implementación debe preparar V0.8, pero no adelantar su alcance.

==================================================
2. ALCANCE
==================================================

V0.7 incluye:

- Un proveedor LLM real.
- Integración con la API del proveedor.
- Configuración mediante ProviderConfig.
- Selección mediante registry.
- Manejo de errores mediante providers.errors.
- Timeout configurable.
- Validación de configuración.
- Tests completamente aislados de Internet.
- Documentación de configuración y uso.
- Actualización del roadmap/versionado.
- Preparación de una API que pueda ser utilizada posteriormente por V0.8.

V0.7 NO incluye:

- RAG.
- Embeddings.
- Vector databases.
- Agentes.
- MCP.
- Tool calling.
- Memoria.
- Chat.

- Integración obligatoria del LLM con Analyzer.
- Integración obligatoria del LLM con Generator.
- Integración obligatoria del LLM con Validator.
- Cambios funcionales en la CLI.
- GUI.
- Entrenamiento de modelos.
- Fine-tuning.

==================================================
3. PROVEEDOR
==================================================

Implementar UN SOLO proveedor real.

Proveedor inicial:

Anthropic.

Clase:

providers/anthropic.py

Debe implementar:

class AnthropicProvider(LLMProvider):
    def generate(self, prompt: str) -> str:
        ...

Debe respetar exactamente:

LLMProvider.generate(prompt: str) -> str

No modificar el contrato existente.

==================================================
4. TRANSPORTE
==================================================

No utilizar el SDK oficial de Anthropic inicialmente.

Utilizar únicamente stdlib cuando sea razonable:

- urllib.request
- urllib.error
- json

No agregar dependencias runtime nuevas salvo que una limitación técnica demostrable lo haga imprescindible.

Si se considera necesaria una dependencia nueva, detenerse y justificarla antes de implementarla.

==================================================
5. CONFIGURACIÓN
==================================================

Reutilizar ProviderConfig de V0.6.

Variables:

SPRING_DOC_LLM_PROVIDER
SPRING_DOC_LLM_MODEL
SPRING_DOC_LLM_API_KEY

Opcionalmente:

SPRING_DOC_LLM_TIMEOUT

El timeout debe tener un valor seguro por defecto.

Nunca:

- hardcodear API keys;
- hardcodear credenciales;
- imprimir API keys;
- incluir API keys en excepciones;
- incluir API keys en tests reales.

El modelo debe poder ser proporcionado mediante ProviderConfig.

==================================================
6. REGISTRY
==================================================

Registrar el nuevo proveedor:

"anthropic" → AnthropicProvider

Debe continuar funcionando:

"fake" → FakeProvider

Ejemplo conceptual:

get_provider(
    ProviderConfig(
        provider="anthropic",
        model="...",
        api_key="..."
    )
)

debe devolver:

AnthropicProvider

Mientras que:

get_provider(
    ProviderConfig(provider="fake")
)

debe devolver:

FakeProvider

UnknownProviderError debe continuar funcionando para providers desconocidos.

==================================================
7. API ANTHROPIC
==================================================

Implementar únicamente la operación mínima necesaria:

prompt → respuesta textual.

No implementar:

- streaming;
- herramientas;
- imágenes;
- archivos;
- conversaciones;
- memoria;
- function calling;
- MCP.

El proveedor debe construir una solicitud HTTP válida y convertir la respuesta del proveedor en:

str

==================================================
8. ERRORES
==================================================

Todas las excepciones externas deben traducirse a providers.errors.

Nunca permitir que el consumidor tenga que conocer urllib.error o excepciones específicas de Anthropic.

Casos mínimos:

- API key ausente → MissingCredentialError
- modelo inválido/configuración inválida → InvalidModelError
- timeout → ProviderTimeoutError
- error HTTP → ProviderRequestError
- respuesta JSON inválida → InvalidResponseError
- respuesta sin texto esperado → InvalidResponseError

Los mensajes de error nunca deben incluir la API key.

==================================================
9. SEGURIDAD
==================================================

La API key:

- solo puede provenir de configuración;
- no puede estar en código;
- no puede aparecer en logs;
- no puede aparecer en repr/str;
- no puede aparecer en mensajes de excepción;
- no puede aparecer en archivos generados;
- no puede aparecer en tests.

Los tests utilizarán credenciales ficticias.

No realizar llamadas reales durante pytest.

==================================================
10. TESTING
==================================================

Todos los tests deben funcionar sin Internet.

Crear como mínimo:

Cubrir:

1. construcción correcta;
2. ausencia de API key;
3. ausencia de modelo cuando sea obligatorio;
4. construcción del request;
5. headers correctos;
6. payload correcto;
7. parseo de respuesta válida;
8. respuesta sin contenido esperado;
9. JSON inválido;
10. timeout;
11. HTTP 4xx;
12. HTTP 5xx;
13. credencial nunca expuesta;
14. registry resuelve "anthropic";
15. FakeProvider continúa funcionando.

Mockear urlopen mediante unittest.mock.

No introducir pytest-mock ni librerías HTTP adicionales sin justificación.
