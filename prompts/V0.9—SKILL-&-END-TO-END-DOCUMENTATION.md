# V0.9 — SKILL & END-TO-END DOCUMENTATION

## Directriz oficial de implementación

### Proyecto

Spring Doc — Motor de documentación automática de microservicios Java Spring Boot.

### Versión objetivo

V0.9.0

### Nombre de la versión

Skill + End-to-End Documentation

---

# 1. OBJETIVO

V0.9 tiene como objetivo conectar las capacidades construidas durante V0.1–V0.8 en un flujo completo de documentación de microservicios Java Spring Boot.

Hasta V0.8 el proyecto dispone de:

- Analyzer para inspeccionar proyectos Java/Spring Boot.
- Generator para producir OpenAPI.
- Validator para validar OpenAPI.
- CLI `spring-doc`.
- Infraestructura desacoplada de LLM providers.
- FakeProvider para testing.
- AnthropicProvider real.
- AI Documentation Foundation.
- Skill independiente para documentar servicios Java/Spring Boot.

V0.9 debe convertir esas piezas en un flujo coherente de extremo a extremo.

El resultado esperado es que una persona pueda entregar un microservicio Java/Spring Boot y obtener documentación técnica enriquecida por IA mediante una Skill que pueda ser utilizada desde distintos agentes/LLM.

La Skill NO debe depender de Claude Code, OpenCode, Codex ni de ningún LLM específico.

Debe ser una instrucción portable.

La IA NO es la fuente de verdad del sistema.

La fuente de verdad es el código del microservicio.

El flujo debe respetar:

    Código
       ↓
    Analyzer
       ↓
    Datos estructurados
       ↓
    OpenAPI base
       ↓
    LLM
       ↓
    Enriquecimiento
       ↓
    Validator
       ↓
    Documentación final

El LLM puede:

- mejorar descripciones;
- explicar comportamiento;
- generar documentación textual;
- resumir endpoints;
- explicar DTOs;
- mejorar títulos y descripciones;
- detectar inconsistencias;

El LLM NO puede:

- inventar endpoints;
- inventar parámetros;
- inventar DTOs;
- inventar respuestas;
- modificar silenciosamente contratos;
- afirmar comportamientos no demostrados por el código;

# 8. RESPONSABILIDAD DE LA SKILL

La Skill debe actuar como orquestador de documentación.

Debe seguir aproximadamente este proceso:

### Paso 1 — Inspección

Identificar:

- raíz del proyecto;
- estructura;
- build system;
- versión Java;
- Spring Boot;
- controllers;
- DTOs;
- configuración relevante.

No modificar código fuente.

### Paso 2 — Análisis

Ejecutar el Analyzer disponible mediante la CLI.

Obtener:

- endpoints;
- controllers;
- parámetros;
- DTOs;
- responses;
- diagnostics.

### Paso 3 — Generación

Generar OpenAPI base utilizando el Generator existente.

### Paso 4 — Validación

Validar el OpenAPI generado.

Si existen errores estructurales:

1. reportarlos;
2. corregir únicamente lo que corresponda al flujo permitido;
3. volver a validar.

No inventar información para ocultar errores.

### Paso 5 — Preparación del contexto

Construir un contexto compacto para el LLM utilizando exclusivamente información derivada del análisis.

No enviar innecesariamente el proyecto completo.

El contexto debe priorizar:

- endpoint;
- método HTTP;
- path;
- parámetros;
- request DTO;
- response DTO;
- códigos de respuesta;
- información disponible en el código;
- OpenAPI generado.

### Paso 6 — Enriquecimiento mediante IA

Solicitar al LLM mejorar la documentación.

El LLM debe producir únicamente información derivada del contexto proporcionado.

### Paso 7 — Integración

Aplicar el resultado del LLM sobre la documentación.

No modificar silenciosamente elementos contractuales descubiertos por el Analyzer.

### Paso 8 — Validación final

Volver a ejecutar Validator.

La documentación final no se considera terminada hasta que pase la validación.

### Paso 9 — Reporte

Informar:

- proyecto procesado;
- endpoints encontrados;
- DTOs encontrados;
- documentación generada;
- warnings;
- errores;
- archivos producidos;
- proveedor utilizado, si corresponde;
- si hubo enriquecimiento mediante IA.

# 10. LLM COMO CAPA DE ENRIQUECIMIENTO

El LLM recibe información estructurada.

Ejemplo conceptual:

```json
{
  "endpoint": {
    "method": "GET",
    "path": "/customers/{id}",
    "parameters": [
      {
        "name": "id",
        "type": "Long",
        "required": true
      }
    ],
    "response": {
      "type": "CustomerResponse"
    }
  }
}





El LLM puede producir:

{
  "summary": "Obtiene un cliente por su identificador",
  "description": "Consulta la información del cliente asociado al identificador proporcionado."
}

Pero no puede producir:

{
  "path": "/customers/search"
}

si ese endpoint no existe en la evidencia proporcionada.

11. REGLA DE NO INVENCIÓN

Toda información generada por IA debe clasificarse conceptualmente como:

Evidencia

Información encontrada directamente en:

código;
Analyzer;
OpenAPI generado;

Inferencia segura

Información textual derivada razonablemente de la evidencia.

Desconocido

Información que no puede determinarse.

omitirlo;
