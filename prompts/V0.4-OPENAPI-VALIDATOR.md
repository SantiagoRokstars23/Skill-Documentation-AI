# V0.4 — OpenAPI Quality Validator

## 1. Objetivo

V0.4 agrega una capa de validación y control de calidad sobre los documentos
OpenAPI 3.0.3 producidos por V0.3.

El objetivo es detectar problemas estructurales, inconsistencias y riesgos
de calidad en el documento generado, utilizando únicamente la información
disponible en el documento OpenAPI y sin volver a analizar código Java.

Flujo objetivo:

Java / Spring Boot
        ↓
Analyzer V0.2
        ↓
AnalysisResult
        ↓
OpenAPI Generator V0.3
        ↓
OpenAPI 3.0.3
        ↓
V0.4 Quality Validator
        ↓
Diagnostics / Quality Report

Antes de modificar cualquier archivo, verificar:

- tag v0.3.0
- commit 18fd398
- working tree limpio
- versión 0.3.0
- 149/149 tests pasando
- generators/ funcionando
- OpenAPI 3.0.3 como versión actual
- existencia de JSON/YAML de ejemplo
- estado actual de analyzer/models.py
- sistema Diagnostic existente

La Fase 1 debe ser exclusivamente de inspección.

No modificar archivos durante Fase 1.


## 3. Alcance de V0.4

V0.4 implementará un Quality Validator propio y acotado.

Debe ser capaz de recibir un documento OpenAPI ya construido y detectar
problemas conocidos dentro del Scope Lock.

El Validator NO debe analizar:

- Java
- AST
- Regex
- Spring Boot
- javalang
- DTOs Java
- código fuente
- AnalysisResult

El Validator trabaja exclusivamente sobre la representación OpenAPI.


## 4. Scope Lock

### INCLUIDO

- validación estructural básica de OpenAPI 3.0.3
- validación de paths
- validación de HTTP methods
- validación de operationId
- validación de parameters
- validación de requestBody
- validación de responses
- validación de schemas
- validación de $ref internos
- detección de referencias inexistentes
- detección de operationId duplicados
- detección de schemas duplicados/inconsistentes cuando sea detectable
- validación de tipos OpenAPI conocidos
- validación de estructuras array/object
- validación básica de security
- validación de información obligatoria del documento
- clasificación ERROR/WARNING/INFO
- reporte determinista
- tests exhaustivos

### EXCLUIDO

No implementar:

- Swagger UI
- Swagger Editor
- OpenAPI Generator oficial
- Swagger Validator
- librerías completas de validación OpenAPI
- validación contra servidores reales
- HTTP
- CLI
- CI/CD
- Docker
- Confluence
- MCP
- RAG
- agentes
- LLM
- Claude
- Gemini
- OpenAI
- generación de SDK
- generación de clientes
- generación de servidores
- HTML
- UI
- base de datos
- almacenamiento persistente
- modificación automática del OpenAPI

V0.4 detecta problemas.

V0.4 NO corrige automáticamente problemas.


## 5. Principio fundamental

El Validator debe seguir el mismo principio permanente introducido en V0.2:

> Evidencia antes que inferencia.

El Validator solo puede reportar problemas que pueda demostrar mediante
la estructura del documento recibido.

No debe inventar información faltante.


## 6. API pública propuesta

La Fase 2 debe evaluar la API exacta.

Como punto de partida se propone:

    validate(document: dict) -> list[Diagnostic]

y opcionalmente:

    validate(document: dict) -> ValidationResult

Si se introduce ValidationResult, deberá justificarse explícitamente por qué
no basta con devolver list[Diagnostic].

También puede existir una API de conveniencia:

    validate_json(text: str)
    validate_yaml(text: str)

pero solamente si la Fase 2 determina que aporta valor real y no genera
duplicación innecesaria.

La API pública deberá estar disponible desde:

    validator/

o la estructura modular que sea aprobada durante la Fase 2.

No modificar analyzer/models.py salvo que la Fase 2 demuestre una necesidad
real e inevitable.

## 8. Severidades

Debe mantenerse:

    ERROR
    WARNING
    INFO

### ERROR

Problemas que hacen que el documento sea estructuralmente inválido
o que una construcción obligatoria esté claramente mal formada.

Ejemplos:

- falta openapi
- falta info obligatoria
- método HTTP inválido
- $ref inexistente
- schema array sin items
- operation sin responses
- parámetro sin nombre
- parámetro sin in
- operationId duplicado cuando la política lo considere inválido

### WARNING

Problemas que no necesariamente invalidan el documento pero representan
riesgos de calidad.

Ejemplos:

- operation sin description
- schema sin description
- response sin description
- security definida mediante extensión propia
- convenciones generadas por V0.3
- schemas sin propiedades cuando se esperaba un objeto

### INFO

Información útil pero no necesariamente problemática.

Ejemplos:

- operaciones sin security
- schemas no referenciados
- convenciones detectadas
- elementos opcionales ausentes

La severidad final de cada regla debe quedar documentada.


## 9. Validaciones obligatorias

### 9.1 Documento raíz

Verificar:

- `openapi` existe
- `openapi` corresponde a 3.0.x
- `info` existe
- `info.title` existe
- `info.version` existe
- `paths` existe cuando corresponda
- tipos básicos de cada propiedad raíz

No asumir que cualquier versión 3.x es equivalente.

V0.4 está diseñado para OpenAPI 3.0.x,
con especial atención a 3.0.3.


## 10. Paths

Validar:

- path comienza con `/`
- path no es vacío
- path parameters están correctamente definidos
- cada operation usa un método HTTP válido
- no existen métodos desconocidos
- cada operation tiene estructura válida

Métodos permitidos:

    get
    put
    post
    delete
    options
    head
    patch
    trace

No aceptar métodos arbitrarios.


## 11. operationId

Validar:

- operationId debe ser string cuando existe
- operationId no debe repetirse globalmente
- detectar colisiones entre paths diferentes
- detectar colisiones entre métodos diferentes

El Validator debe recorrer las operaciones en un orden determinista.

Nunca depender del orden accidental del dict de entrada para producir
diagnósticos.


## 12. Parameters

Validar parámetros:

- `name`
- `in`
- estructura del Parameter Object
- `in` permitido:
  - path
  - query
  - header
  - cookie
- path parameters deben tener `required: true`
- schema debe existir cuando corresponda
- no duplicar el mismo parámetro dentro del mismo scope
- distinguir parámetros de path y operation

Validar conflictos entre parámetros heredados del Path Item y parámetros
de Operation cuando sean detectables.


## 13. Request Body

Cuando exista `requestBody`:

- debe ser objeto
- `content` debe existir cuando corresponda
- media types deben ser strings válidos
- cada Media Type Object debe tener estructura válida
- schema debe ser válido si está presente
- evitar content vacío cuando sea estructuralmente inválido

No asumir automáticamente:

    application/json

El Validator debe validar lo recibido.

La convención application/json introducida por V0.3 pertenece al Generator,
no debe convertirse en una regla universal del Validator.


## 14. Responses

Toda operation debe tener:

    responses

y responses debe ser un objeto válido.

Cada response debe tener:

    description

Validar:

- status codes válidos
- `default`
- estructura de Response Object
- content
- headers
- links cuando sean presentes
- schemas dentro de content

No inventar responses faltantes.

Si falta responses:

    ERROR


## 15. Status Codes

Aceptar:

- códigos HTTP de tres dígitos
- `default`

Validar que las claves no sean arbitrarias.

No intentar comprobar si el status code corresponde semánticamente al
comportamiento real del código Java.

Eso pertenece al futuro Drift Detection y está fuera del alcance.


## 16. Schemas

Validar schemas OpenAPI 3.0.x.

Tipos principales:

    string
    number
    integer
    boolean
    array
    object

Validar reglas básicas:

### array

Si:

    type: array

debe existir:

    items

### object

Validar coherencia de:

- properties
- required
- additionalProperties
- type

### string

Validar coherencia básica de:

- format
- minLength
- maxLength
- pattern
- enum

### number/integer

Validar coherencia de:

- minimum
- maximum
- exclusiveMinimum
- exclusiveMaximum
- multipleOf
- enum

No implementar JSON Schema completo.


## 17. Enum

Cuando exista:

    enum

validar:

- debe ser array
- no debe contener duplicados cuando la política aprobada lo determine
- los valores deben ser compatibles con el tipo cuando pueda demostrarse

No inferir tipos complejos que no estén explícitamente presentes.


## 18. $ref

Validar referencias internas:

    #/components/schemas/Customer

Debe existir:

    components.schemas.Customer

Detectar:

- $ref inexistente
- $ref vacío
- $ref con estructura inválida

V0.4 no necesita implementar referencias externas.

No descargar URLs.

No realizar llamadas HTTP.


## 19. Components

Validar:

    components

y específicamente:

    components.schemas
    components.parameters
    components.responses
    components.requestBodies
    components.securitySchemes

solo cuando estén presentes.

No exigir que existan todos.

Detectar estructuras incorrectas.


## 20. Security

Validar de forma conservadora.

No interpretar OAuth, JWT, API keys, etc. más allá de la estructura OpenAPI
explícita.

Si existe:

    components.securitySchemes

validar que cada Security Scheme tenga una estructura compatible con su:

    type

Tipos principales:

    apiKey
    http
    oauth2
    openIdConnect

No implementar validación exhaustiva de OAuth flows.

No convertir:

    x-security-evidence

en un securityScheme real.

La extensión de evidencia creada en V0.3 debe permanecer una extensión
informativa.


## 21. Extensions

Las propiedades que empiezan por:

    x-

son extensiones OpenAPI.

V0.4 no debe rechazarlas simplemente por ser desconocidas.

No obstante, extensiones conocidas por V0.3 pueden recibir validaciones
específicas si existe evidencia suficiente.


## 22. Determinismo

La salida del Validator debe ser determinista.

Para el mismo documento:

    validate(document)

debe producir exactamente los mismos diagnostics en el mismo orden.

No utilizar:

- hash aleatorio
- UUID
- timestamp
- memoria
- orden accidental de sets

Cuando sea necesario ordenar:

- paths por nombre
- methods por nombre
- operationId por valor
- schemas por nombre
- referencias por valor

La política exacta debe documentarse.


## 23. No modificación

El Validator debe ser una operación de solo lectura.

No puede:

- modificar el dict recibido
- insertar propiedades
- eliminar propiedades
- normalizar silenciosamente
- corregir errores
- cambiar operationId
- generar schemas
- completar responses

La entrada debe permanecer intacta después de validar.


## 24. Separación Generator / Validator

Debe mantenerse estrictamente:

    Generator → produce OpenAPI

    Validator → analiza OpenAPI

El Validator no debe llamar al Generator.

El Generator no debe llamar al Validator automáticamente salvo que la Fase 2
autorice explícitamente una integración opcional.

Por defecto serán componentes independientes.


## 25. Dependencias

No agregar automáticamente una librería completa de validación OpenAPI.

No utilizar:

- openapi-core
- prance
- openapi-spec-validator
- swagger-parser
- jsonschema como sustituto de un validador OpenAPI

La validación será propia y limitada al Scope Lock.

La stdlib debe utilizarse siempre que sea suficiente.

PyYAML ya forma parte de V0.3 y puede reutilizarse para parsear YAML.

No agregar otra dependencia únicamente para V0.4 sin una justificación
arquitectónica explícita.


## 26. Parser JSON/YAML

Si se implementan APIs:

    validate_json(...)
    validate_yaml(...)

deben:

- parsear la entrada
- capturar errores de sintaxis
- devolver diagnostics
- nunca lanzar una excepción no controlada ante input inválido

Los errores de parseo deben distinguirse de errores estructurales.

Ejemplo:

    OPENAPI_JSON_PARSE_ERROR
    OPENAPI_YAML_PARSE_ERROR

## 28. Test de inmutabilidad

Debe existir al menos un test que demuestre:

    original == deepcopy(original)

después de ejecutar:

    validate(original)

Esto garantiza que el Validator sea realmente de solo lectura.


## 29. Test de determinismo

Ejecutar:

    validate(document)

varias veces y comprobar igualdad exacta de diagnostics.

También debe verificarse con documentos construidos en órdenes diferentes
cuando el contenido semántico sea equivalente.


## 30. Integración con V0.3

No modificar la salida del Generator como parte de V0.4.

El archivo:

    examples/customer-service/openapi.json

y:

    examples/customer-service/openapi.yaml

deben continuar siendo productos del Generator V0.3.

V0.4 puede consumirlos en tests, pero no reemplazarlos ni modificarlos
automáticamente.


## 31. Arquitectura

Durante Fase 2 deberán evaluarse al menos dos alternativas:

### Alternativa A

Un único:

    validator/openapi_validator.py

### Alternativa B

Estructura modular pequeña:

    validator/
        __init__.py
        openapi_validator.py
        openapi_rules.py

No crear módulos adicionales sin justificación.

La arquitectura elegida debe priorizar:

- cohesión
- bajo acoplamiento
- testabilidad
- determinismo
- facilidad de extensión


## 32. Regla contra sobreingeniería

No construir un parser completo de la especificación OpenAPI.

No crear dataclasses para cada objeto OpenAPI.

No reproducir toda la especificación como clases Python.

No implementar JSON Schema completo.

No implementar un sistema genérico de reglas excesivamente abstracto.

La solución debe ser proporcional al alcance de V0.4.

2. La API pública esté definida.
3. Se reutilice Diagnostic existente.
4. No se modifique Analyzer sin justificación.
5. No se agregue un validador OpenAPI externo.
6. OpenAPI 3.0.3 sea correctamente soportado.
7. Se validen paths.
8. Se validen methods.
9. Se validen operationId.
10. Se validen parameters.
11. Se valide requestBody.
12. Se validen responses.
13. Se validen schemas.
14. Se validen arrays.
15. Se validen objects.
16. Se validen enums.
17. Se validen $ref internos.
18. Se validen components.
19. Se valide security de forma conservadora.
20. Se manejen JSON/YAML inválidos si esas APIs son implementadas.
21. Los diagnostics sean deterministas.
22. El Validator no modifique la entrada.

27. La documentación coincida con el comportamiento real.
28. No existan secretos ni artefactos accidentales.
29. La revisión pre-commit sea satisfactoria.
30. Se realice commit y tag únicamente después de autorización.

## 37. Regla final

V0.4 no debe convertirse en un reemplazo de un validador oficial de OpenAPI.

El objetivo es construir una capa propia, pequeña, determinista y explicable
que permita detectar problemas frecuentes y relevantes en los documentos
OpenAPI generados por este proyecto.

La prioridad continúa siendo:

    evidencia
    determinismo
    compatibilidad
    explicabilidad
    tests
    simplicidad

antes que cobertura indiscriminada de la especificación.
